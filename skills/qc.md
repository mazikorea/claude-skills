# QC

<!-- QC_CORE_VERSION: 2026-08-14-v1 -->

## 목적

결과만 검사하지 말고 기존 맥락, 업무 의도, 효과성, 효율성, 운영 구조 적합성까지 확인한다. 검토는 깊게 수행하고 보고는 짧게 쓴다.

## 검토 모델 (필수, 2026-11-04 사용자 지시)

- 판정자: **Claude Opus 5.5 (`claude-opus-5-5`) + 추론 강도 xhigh** 독립 서브에이전트.
- Agent 호출: `model: "opus"`, `effort: "xhigh"`. 호출 전 `opus` 별칭이 Opus 5.5인지 확인하고, 다른 버전을 가리키면 보고에 실제 버전을 적는다.
- 판정자는 원천(코드·receipt·live readback·운영 규칙)을 직접 읽는다. 부모는 핵심 근거를 원천과 재대조한 뒤 확정한다.
- 비례 적용(2026-11-07): `Lite` 모드는 부모가 직접 원천을 읽고 판정한다(판정자 생략). Opus xhigh 판정자는 `Deep` 모드에서만 띄운다.
- 보고 첫 줄에 `검토 모델: Opus 5.5 xhigh`를 표기한다. 다른 모델·강도로 돌렸으면 그 사실과 이유를 표기한다.

## 모드

- `Lite`: 과거 결정에 의존하지 않는 저위험 설명·단순 산출물. 현재 요청, governing rule, 원천, 결과를 확인한다.
- `Deep`: `기존/전에/다시/이어서/수정/교정/인수인계/원래 목적/구조/전략/QC`가 나오거나 외부 공유·비용·권한·production·여러 호스트가 얽힌 작업. 단, `QC`·`수정`·`다시` 단어만 있고 대상이 소규모·백업 있는 변경이면 Lite. 관련 히스토리와 현재 상태를 함께 확인한다.

## 1. 맥락·의도 게이트

판정 전에 내부적으로 아래를 확정한다.

- `목적`: 최종적으로 만들 결과
- `의도`: 왜 필요한지와 사용자가 중요하게 보는 기준
- `기존 결정`: 유지해야 할 최신 결정·교정
- `금지·제약`: 하지 말아야 할 것과 승인 경계
- `성공 조건`: 완료를 증명할 객관적 상태

과거 업무에 의존하면 현재 thread → 관련 세션 원문 → governing skill/AGENTS/KB → `CURRENT-STATE.md` → 실제 대상 순으로 필요한 부분만 검색한다. 모든 기록을 통째로 넣지 말고 최신 결정과 충돌 후보를 찾은 뒤 필요한 원문만 확장한다. 근거 없이 기억한다고 말하지 않는다.

맥락을 확인할 수 없고 그 누락이 판정에 영향을 주면 `PASS`를 금지하고 `UNVERIFIED`로 판정한다. 사용자의 미공개 의도처럼 조사할 수 없는 결정만 질문한다.

## 2. 제안 품질 게이트

- `효과성`: 제안이 목적과 성공 조건을 직접 달성하는가.
- `효율성`: 비용, 시간, 토큰, 운영 리소스, 사용자 개입이 더 적은 대안이 있는가.
- `구조 적합성`: 기존 스킬, 에이전트, 프로필, 메모리, 자동화, canonical 원천을 재사용하는가.
- `중복·운영비`: 새 도구·DB·cron·프로필·로그인·동기화를 불필요하게 늘리지 않는가.
- `안전·복구`: 승인 경계, 실패 격리, 롤백, 가용성 저하 시 경로가 있는가.
- `검증 가능성`: 제안 성공을 readback·smoke·원천 대조로 확인할 수 있는가.

구조 변경은 가능하면 `현행 유지 / 최소 수정 / 신규 구축`을 비교하고 목적을 충족하는 가장 단순한 안을 추천한다. 기존 기능으로 충분한데 새 시스템을 추가한 제안은 WARN 또는 FAIL이다.

## 3. 산출물·실행 게이트

- 요청 범위와 실제 검수 범위를 맞춘다.
- 원천 데이터와 산출물, 날짜·통화·퍼센트·수량·모수·기간·단위를 맞춘다.
- 외부 발송·삭제·결제·권한 변경·대량 쓰기는 preview와 명시 승인을 확인한다.
- 비밀번호 변경·재설정·복구·초기화·임시 발급·우회는 수행하지 않는다.
- 계획, 명령 성공, 코드·테스트 통과, handoff 문구만으로 완료 처리하지 않는다.
- 실제 대상에서 readback, smoke, 렌더링, 샘플 대조 중 적합한 검증을 수행한다.

## 채널 어드민 추가 게이트

- 정확한 계정·브랜드·매장 조합과 기존 canonical 로그인 세션을 먼저 확인한다.
- 살아 있는 정상 세션이면 새 로그인·프로필을 만들지 않고 재사용한다.
- Koko는 가용성을 확인하고, 불가하면 Buddy 또는 승인된 경로를 사용한다.
- 동일 실제 계정의 인증 owner는 하나로 유지한다.
- 코드 성공과 실제 보호 페이지·다음 실행·중복 로그인/OTP 상태를 분리해 검증한다.

## 판정

- `PASS`: 목적·맥락·효과·효율·구조·안전·실제 검증이 충족됨.
- `WARN`: 사용할 수 있지만 근거, 효율, 구조 적합성, 운영 안정성 보완이 필요함.
- `FAIL`: 목적과 어긋나거나 위험·오류·중복 구축 때문에 사용·발송·반영하면 안 됨.
- `UNVERIFIED`: 필요한 세션·원천·호스트·live 상태에 접근하지 못해 결론을 확정할 수 없음.

## 합리적 추정·신뢰도

**"합리적 추정"의 정의**: 직관/감 X. 검증 가능한 데이터·논리·교차 검증으로 근사치 산출.

**합리적 추정 5조건** (모두 충족 못하면 "추측" → 사용 금지):
1. 출처 1개 이상 명시
2. 계산 과정 재현 가능 (숫자의 출처·산출식 노출)
3. 교차 검증 1회 이상 (또는 한계 명시)
4. 대안값 비교 (저/중/고 시나리오 또는 다른 방법론)
5. 신뢰도·한계 명시 (★ + 어떤 가정에 민감한지)

**신뢰도 올리는 5가지 방법**:
1. **1차 자료**: DART·통계청·감사보고서 직접 (매체 인용보다 ★ 1단↑)
2. **교차 검증**: 다른 방법론으로 같은 결론 (★ 1단↑)
3. **백트래킹**: 추정 합계 = 실제 알려진 합계 일치 (★ 1단↑)
4. **시나리오**: 저/중/고 범위 제시 (단일값 X)
5. **삼각측량**: 3가지 다른 추정법 비교 (예: 인구×단가 + 글로벌비율 + Top합계)

**출처·추정 신뢰도 표기**:

| 표기 | 신뢰도 | 출처 종류 |
|------|-------|----------|
| ★★★ | 90~100% | DART 공시·통계청·감사보고서·OECD/IMF, 또는 복수 1차 자료 교차 |
| ★★ | 70~89% | 패션비즈·한국경제·트랜드리서치·유로모니터·Statista 등 신뢰 매체 단일 |
| ★ | 50~69% | 단일 매체 + 추정, 글로벌 자료 한국 환산, 인터뷰 인용 |
| ☆ | 30~49% | 합리적 추론만 (인구×단가 등). 외부 자료 부재 |
| ⚠️ | <30% | 직관 기반. 사용 지양. 사용 시 "의사결정 근거 부적합" 명시 |

**표기 형식**: `약 4,300억 (★, 신뢰도 60%, 인구통계 + 1인당 단가 추정. 1인당 단가가 ±20% 변동 시 결과 ±15%)`

**파생 규칙**: 합산·비중 등 파생 수치 신뢰도 = 입력 중 가장 낮은 신뢰도 따름

## 축약 출력

기본 출력은 필요한 항목만 2~4줄로 쓴다.

- `판정`: PASS / WARN / FAIL / UNVERIFIED와 한 줄 결론
- `핵심`: 목적 적합성 또는 가장 중요한 문제
- `수정`: WARN/FAIL일 때 최소 수정안
- `근거`: 확인한 세션·원천·readback

내부 체크리스트와 긴 로그는 출력하지 않는다. 과거 결정 충돌, 고위험 작업, 복수 오류, 사용자의 상세 요청이 있을 때만 확장한다. 실제 사용자 결정이나 human boundary가 없으면 `사용자가 할 일`을 만들지 않는다.
